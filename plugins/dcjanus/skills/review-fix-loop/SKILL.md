# Review Fix Loop

确定审查目标、base、当前版本及本次允许的修复与发布范围。仅要求审查时交付 findings；用户限定本地修改时，在工作树中完成修复和复审。涉及提交、推送或平台写入时遵循已有授权和对应的仓库、平台 skill，保留用户已有改动。

## 每批审查

1. 给三位 reviewer 相同的简报，列出原需求、仓库路径、base 与待审版本（含本地差异），以及有证据可复查的验证结果和已排除的问题。提供必要的风险背景，避免预设结论。
2. 并行启动三位全新上下文的 reviewer，只读审查同一份最终差异。按实际工具显式关闭继承（如 `fork_turns="none"` 或 `fork_context=false`），不让 reviewer 看到父线程或彼此输出。无法隔离时停止循环并说明限制。
3. 要求每位 reviewer 给出问题位置、触发条件、影响及依据；没有可操作的问题就明确说明。简报与 diff 或平台状态冲突时，以可核实的证据为准。
4. 收齐三份完整报告后，由主线程去重并复核。接受能指出具体回归、兼容性破坏、CI 故障或对外行为测试缺口的意见；不因人数或风格偏好自动改代码。按工具能力释放已完成的 reviewer。
5. 同一批三份报告均无有效意见即结束。否则修复已确认的问题，完成对应验证，完整循环默认提交并推送本轮修复；若用户限定本地则直接复审工作树。再对新版本启动完整的一批。验证失败先修复；版本变化后旧报告不能用于验收。

超时先核实 reviewer 是否仍在运行。缺少完整报告的批次不能通过；确认中断后重新启动整批。用户要求暂停时，记录当前版本、已接受的问题和待办。

逐批简报三位 reviewer 的发现、主线程采纳或拒绝的理由及实际修复、验证和发布状态。结束时说明最终一批审查的版本、结论及仍影响使用的风险。
