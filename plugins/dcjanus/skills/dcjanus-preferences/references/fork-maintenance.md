# 长期自用 Fork 维护偏好

适用于持续使用并维护自己改造的 fork，不适用于仅为向上游贡献 PR 而建立的临时 fork。具体操作遵循目标仓库的 `AGENTS.md` 和维护 skill。

## 分支与提交

- 一个长期主分支包含选定的上游基线与全部自有改造，日常直接在该分支维护；不以长期功能分支或 stacked PR 管理整套 fork。临时验证分支和 worktree 完成用途后清理。
- `origin` 指向自用 fork，`upstream` 指向原项目；操作前核对真实 URL、默认分支和本地/远端关系。
- 按修改目的组织清晰的英文 Conventional Commits；一个改造可以有多个实现、测试和修正 commit，不强求“一改造一提交”，也不把整套 fork squash 成一笔。
- 主分支直接维护、上游同步与历史改写是不同操作。此偏好不额外授予 commit、push 或强推权限；普通开发保留历史，同步上游按项目规则及当前任务授权处理。

## 上游基线与同步

- 用受版本管理的文件记录明确的上游 tag 或 commit，并确认其为当前 fork 的祖先；以该基线到 HEAD 的净 diff 识别自有改造，不把旧 PR 或不准确的 merge-base 当作补丁范围。
- 基线选择按产品需要：可跟进指定发行渠道的已发布 tag，也可跟进上游开发分支的精确 commit。每轮开始确定同步目标，避免在同一轮中反复追逐移动的上游版本；选定的渠道和记录方式由目标仓库约定。
- 同步时将自有提交 rebase 到新基线，按原修改目的适配上游结构；确认旧基线边界，避免上游改写历史后把旧上游提交误当作自有补丁重放。
- 使用净 diff、必要的 range-diff 和专项回归检查遗漏、重复与行为回退；没有文本冲突不代表改造仍然完整。上游已吸收同一目的时，确认行为后删除重复实现或缩小差异。
- 历史重放前保存可恢复的旧状态；风险较高时在临时 worktree 演练。需要改写远端历史时，用同步前记录的精确旧 SHA 做 force-with-lease；远端变化后重新整合验证。
- 完成适配与验证后更新基线记录；交付时概述主要上游功能或维护变化，以及哪些 fork 改造仅重放、需要适配或已被吸收。

## 编号改造记录

- 在 `docs/fork-changes/README.md` 维护索引，每个改造对应一个 `NNNN-主题.md`，解释目的、当前行为、代码入口、验证依据及上游同步边界。
- 新改造取下一个编号；已有改造继续更新原记录，代码与相关说明一并交付。编号代表长期改造点，不绑定 PR、分支、commit SHA 或固定提交数。
- 上游吸收或移除改造后保留原编号和记录，注明状态、吸收基线及残留差异；“维护中”只说明仍有改造，不替代 CI、发布或安装验收。
- 只维护长期有效的行为与约束。单次冲突、排错和执行流水放在当次交付说明，实际语义或长期同步要求改变时再更新改造记录。

## CI、分发与验收边界

- 先遵循 [私有仓库与 Actions 成本偏好](repository-maintenance.md#私有仓库与-actions-成本) 确认是否启用 Actions，再决定以下验证与分发范围。
- 按自用需求裁剪上游自动化，保留必要验证和自己的分发流程；同步时复核 workflow，避免重新启用上游网站部署、官方发布渠道、CLA 或 PR 治理等不需要的自动化。
- 不需要公开分发时可仅保留验证 CI；需要独立分发时再增加自有版本、构建、发布与安装器。多平台范围、签名与保留策略按目标产品决定。
- 本地资源有限时优先完成格式、静态检查和定向回归，将重型测试与构建交给 CI；本地与 CI 的验证分工以目标仓库的资源约束和验证需求为准。
- 分别验收源码与测试、最新 SHA 的 CI、发布产物、实际安装和运行行为。发布成功不等于本机已更新；隔离包验收完成后，才在授权范围内替换日常安装。
