# 事项与进展

创建、编辑、拆分、关联或收尾 Issue，以及写 Comment 前读取。查询既有记录只需入口中的查询约定。

## 决定记录什么

一个 Issue 表达一个值得再次投入注意力、可独立判断结果的目标。临时步骤、纯信息和长期参考资料不机械建单；资料使用 Document，需要推进的后续目标另建 Issue 并引用资料。

查重比较目标、完成条件、来源和交付物，覆盖打开、关闭及必要的归档事项。相同目标复用原事项；前一目标已结束、新工作能独立验收时才新建。

拆分只用于需要独立状态或验收的组成结果。父 Issue 保留整体目标、共同验收条件和跨事项约束；子 Issue 只描述自身任务，子项完成不自动证明父项目标达成。

## 把信息放到正确位置

- Description 保存稳定的背景、目标、范围、注意事项、完成条件和初始来源。只有任务定义变化或事实需修正时才改写；不要用阶段总结覆盖原目标。
- Comment 按时间记录进展、决策、等待对象、恢复条件、下一步和交付证据，以及完成或取消原因。保留必要结论与证据链接，不复制完整外部记录或命令流水账。
- 父子、阻塞、相关和重复使用 Linear 原生关联。不要在正文再维护关系清单，或复制关联事项的标题、状态和逐项目标。
- 只有前置未满足就无法继续或验收时才设阻塞；普通关联用 Related。可以用 Comment 解释原因；外部审批或反馈没有对应 Issue 时，直接记录真实对象与证据，不为建立关系虚构 Issue。
- Priority、Due date、状态和负责人使用原生字段，不用正文代替。日期与承诺从用户或来源取得，不虚构期限；创建时显式选择到期日或无到期日，默认状态和负责人可从 `issue create --help` 确认。

## 写入与收尾

复杂正文使用 `--description-file`，Comment 使用 `--body-file`；正文先保存在可审阅的 UTF-8 文件中。写前按入口的授权和预览约定执行，写后核对字段；关系操作核对两端。

Comment 创建会在 Codex 环境默认附带“在 Codex 中继续”的恢复入口；不要自行拼接。只有明确不需要时才使用 `--no-codex-resume`。

完成、取消和重复分别表达达标、目标失效和由另一事项承载；记录对应结果与原因。归档、恢复和删除使用 `issue archive/restore/delete`；普通删除可恢复，永久删除仅用于管理员明确授权的不可恢复清理。不要把整理事项扩大为批量删除。
