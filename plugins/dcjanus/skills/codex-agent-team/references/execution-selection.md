# 任务与执行选择

## 协作收益与执行载体

先读相关源码、调用关系和项目约定，确认任务能否依据明确输入独立完成并验收。共享背景过多、输入快速变化或交接成本超过收益时，由一个 Agent 处理更合适；等待同一资源的任务也不会因为多个 Agent 而并行。

时长只是线索。更关键的是：只需要一次结果，还是需要保留可持续跟进的责任范围；是否需要独立上下文、用户直接参与、跨项目或 host，以及执行载体实际支持的生命周期。

| 方式 | 典型选择 | 责任与生命周期 |
| --- | --- | --- |
| 主 thread 直接完成 | 很小的改动、当前上下文中的决策、强耦合步骤、交接成本更高的工作 | 直接实现和验证，不额外委派 |
| 内部 subagent | 定向调查、独立评审、一次实验、边界明确的实现或验证 | 属于当前任务，返回可验收结果后回收；必要时围绕同一责任范围跟进 |
| 用户可见独立 thread | 较长周期功能或迁移、多轮反馈和交付、需要用户单独跟进的工作 | 保留独立上下文与交付身份，显式跟踪依赖、消息和结果 |

subagent 可以做复杂工作，也可能支持恢复；独立 thread 也可以完成短任务。不要把时长惯例写成技术限制，或承诺独立会话永久运行、subagent 自动持久化。使用独立 thread 仍需满足工具的直接人类创建授权。

两种载体可组合：长期 worker 可在已有权限内用局部 subagent 调查、实现或评审，并负责汇总与验收子结果。不要默认层层递归，只有子任务能独立验收且收益超过新增协调成本时才继续拆分。

## 常见协作方式

| 场景 | 协作方式 | 需要避免 |
| --- | --- | --- |
| 大量搜索、日志或资料分析 | subagent 在独立上下文读取，返回结论、证据入口和不确定性 | 将中间噪声全灌回主上下文；结果没有证据可复查 |
| 已明确接口的多项实现 | 按可观察行为或责任范围拆分，必要时隔离工作区 | 仅按文件数量拆分；各自猜测共享接口 |
| 故障有多种合理假设 | 并行做有界实验，记录假设、环境及排除或支持证据，再收敛 | 多个 Agent 同时修改现场，导致无法归因 |
| 实现需要独立审查 | reviewer 看原始需求、最终 diff 和证据，必要时复现发现 | 只给实现者结论；把多个相似答案当质量保证 |
| 前后置流水工作 | 固定可消费契约或 SHA，前置验收后持续启动消费者 | 等整批完成；把“可消费”写成“已合入” |
| 已有 thread 临时争用资源 | 只做发现、通信、占用和释放协商，见 [资源协调](communication-and-resources.md) | 重建团队、抢占资源、建立永久主从关系 |
| 任务扩大、失败或需换模型 | 安全停点整理已做工作、未提交改动和剩余责任，再接管或重派 | 重复实现；将旧验证套到新版本 |

不要求每次设独立 planner、reviewer 或 integrator。主 thread 保留端到端责任；只有规划、审查或集成实际成为瓶颈时，才委派边界清晰的辅助工作，并由明确负责人维护最终集成状态。

## 模型与推理强度

- 简单、明确、低风险且容易验证的任务，优先考虑当前可用的快速模型；任务很小时直接做。
- 歧义较大、跨模块耦合、高风险修改、复杂推理或困难验收，保留给主 thread 或适合的更强模型。长任务中也可以有适合快速模型的阶段。
- subagent 与独立 thread 都可考虑不同档位。先遵循人类指定、预算、项目规则与工具权限，再从当前可用模型及推理强度选择，不从旧列表或名称猜测能力。
- 自主选型获准且工具支持时传所选值；若工具要求人类明确指定具体模型，先满足该条件。没有相应参数或授权时沿用默认，不为更换模型改配置或启动其它进程。
- 不把“强模型规划、快速模型执行”写成固定模板：明确简报能减少执行歧义，但某些实现和验证仍需强模型。根据实际返工调整，不用单位 token 价格代替总交付成本。
- 快速模型遇到超范围歧义、验证失败或反复无进展时，主 thread 查看证据后接管或在权限内升级。先确认原执行者停点和改动归属，避免并发覆盖。

Desktop 新 thread 默认模型、CLI 源模型继承及跟进消息保留目标设置的区别，见 [会话工具](thread-tools.md)。

## 干净上下文与 fork

上下文选择独立于模型、生命周期和工作区。新会话需要什么信息，比已经积累多少历史更重要。

| 策略 | 优先使用的条件 | 交接要求 |
| --- | --- | --- |
| 干净上下文 | 范围与验收明确，可用简报和证据入口独立执行；独立探索或评审需要减少锚定 | 目标、必要决策、原始证据、执行目录、约束和返回要求；不只给结论 |
| fork 既有上下文 | 依赖大量相关决策、讨论、失败尝试或调查现场，重新整理容易遗漏且成本明显更高 | 说明历史截点、新范围、已有决策中哪些仍有效、停止条件和交付责任 |

默认优先精简、可执行的干净简报；不要为了省写简报复制大量无关历史。fork 也不是严格复现同一状态：工具可能只复制已完成 turn，可能包含中断中的 turn；文件系统和外部资源仍可能已变化。创建后核实基线与任务，不继续父会话未完成的所有工作。

独立评审优先原始需求与实际 diff；只有共享讨论对理解契约确有必要时才引入相应历史。fork 继承的结论仍可质疑，继承的指令不扩大原始人类授权。

先读 [会话工具](thread-tools.md) 确认 `create_thread` 与 `fork_thread` 的参数、历史截点及是否启动首轮。不把 create 的 model/title/target 参数套到 fork；fork 不支持创建时覆盖模型时，按后续工具与授权处理，否则保留原设置。subagent 的上下文继承也只用当前 spawn 接口支持的方式，不把独立 thread 的 fork 当作内部 subagent。

## 持续调度与阶段交接

为即将派出的任务明确目标、输入、完成条件与负责人；后续任务保留真实依赖，不提前锁定尚未稳定的路径和接口。依赖出现环、热点重叠或多个任务需要同一决策时，先合并范围或由一个负责人稳定契约。

就绪且资源可用时持续派工，不等待无关任务整批完成。主 thread 在等待间隙审查结果、处理资源请求和更新后续范围，不重复已派出的实现。验证或审查积压时先收敛交付，再增加并行度。

短期任务扩大为持续工作时，不假定工具能将 subagent 原地转换为独立 thread。先保留结论、证据、diff/ref、工作区和剩余任务，确认写入已停；有创建授权时再交接，否则由主 thread 或现有 worker 继续。反向拆分同样固定归属，避免旧、新执行者同时操作。

## 设计依据与取舍

以下是策略依据，不是 Codex 工具契约；当前工具定义与人类要求优先。

- [Claude Code subagents](https://code.claude.com/docs/en/sub-agents) 与 [agent teams](https://code.claude.com/docs/en/agent-teams)：借鉴集中任务回传与独立会话协作的区别，以及 subagent 可恢复的事实；不复制工具、权限或团队运行时。
- [Claude Code 独立会话](https://code.claude.com/docs/en/agent-view)：借鉴会话可独立跟进和选择模型的概念；不据此推定 Codex 后台存活、消息或模型权限。
- [OpenAI subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)：借鉴上下文隔离与按任务配置模型；不固定某个当前型号。
- [Anthropic 多 Agent 研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)：借鉴独立探索、压缩结果和协调成本判断；不将研究评测收益推广为编码加速保证。
- [Cursor 长任务协作实验](https://cursor.com/blog/self-driving-codebases)：借鉴持续调度与角色责任，避免整批等待、无归属协调和单点积压；不采用其允许损坏提交、弱化发布门禁等吞吐取舍。
- [Cursor 模型组合实验](https://cursor.com/blog/agent-swarm-model-economics)：借鉴按职责评估不同模型组合与总成本；不把单一实验的速度、价格或质量结论当作普遍保证。
