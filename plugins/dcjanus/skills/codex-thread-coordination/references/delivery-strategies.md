# 交付与集成方式

把工作会话的交付单位、依赖消费方式和最终发布形式分别确定。人类已明确要求 PR/MR 或项目要求每项独立审查时遵循该要求；其它情况下按依赖、审查成本和平台能力选用最轻的可追溯方式，不把一任务一 PR/MR 写成通用前提。

## 选择方式

| 方式 | 适用条件 | 工作会话交付 | 主会话责任 |
| --- | --- | --- | --- |
| 本地变更交付，汇总发布 | 共享仓库可访问，允许本地提交与集成，希望减少小 PR/MR 开销 | 独立 worktree 的 branch/ref、base/head SHA、变更范围和验证报告 | 逐项验收，在独立集成 worktree 中组合验证，再按授权汇总为一个或少量 PR/MR |
| 独立 PR/MR | 每项能独立合入，或人类/项目要求各自平台审查 | 分支、固定 SHA、URL 和验证报告 | 回读平台、验收并按合入权限处理 |
| 仅工作区修改 | 未授权 commit 或仅要求本地修改 | worktree、明确 diff、验证报告及未提交状态 | 保留已有改动，验收本地结果，不扩大为提交或发布 |

无明确指定时，可采用本地变更交付、汇总发布，前提是相应 commit 和集成操作已有授权；权限不足时采用仅工作区修改。不要为选择交付形式重复询问已覆盖的权限。push、平台发布、正式合入和历史改写仍分别遵循授权。

本地集成只组合和验证已授权范围的变更，不更新受保护目标分支或远端。使用独立集成 worktree，记录起始基线及每项来源 SHA；指定一个集成人串行管理集成 ref。存在多仓库或跨 host 时，先确定可访问的 ref 或授权的传递方式，不假定工作会话共享磁盘。

消费者可以从约定的、已验收可消费的前置提交开始，不必等待一个并未要求创建的 PR/MR。简报记录直接父 SHA、已具备的契约、剩余缺口和验证条件；工作会话只能确认该版本可用，不能宣称它已正式合入。前置被修改时暂停受影响的消费，先由主会话确定新基线及同步责任，再重新验证相关路径。项目要求主线前置时，仍等待实际合入。

不是每个内部分支都必须单独满足最终发布门禁，但简报必须明确允许的临时缺口及可消费条件。最终组合必须满足项目门禁，不提前把已知损坏状态合入目标分支。独立任务从共同基线开始，消费者仅在有真实依赖时基于约定的前置提交开发。

## 合入通知与 worker rebase

使用 Git 原生分支、worktree 和 rebase；不引入额外的分支调度工具。主会话串行管理目标或集成 ref，各工作会话只更新自己的分支和 worktree。

1. **主会话确认实际结果再通知**：核实合入或本地集成确已发生，发送任务来源 head、集成方式、目标 ref、旧/新目标 SHA、已覆盖的前置范围、影响及需补充的验证。区分本地集成与正式合入。跨 host 时提供已授权且可取得的 ref；消息送达只表示已发送，账本仍标记待更新。
2. **工作会话在自己的 worktree 同步**：核对分支、通知身份及固定目标 SHA，在安全检查点保留未提交工作，再按已有授权 rebase。不得替其它工作会话改 ref 或 checkout。无关任务可继续实现，在下次验收前更新；短时间内连续收到多次集成通知时，可确认覆盖关系后合并为最新已核实基线的一次同步。
3. **只重放自己的增量**：先检查实际祖先关系和自身提交范围。前置经 squash、cherry-pick 或改写后合入时，旧前置 SHA 可能已不在新目标历史中，不能盲目重放整个分支。例如原分支基于 A 的固定 head，A 被 squash 集成后，可在确认边界后用 `git rebase --no-update-refs --onto <新目标SHA> <旧前置SHA> <自身分支>`，仅重放 A 之后的自身提交，并避免配置自动移动其它分支；普通分支按实际历史选择 rebase 范围。已有 merge 提交时核实是否需保留合并拓扑，不机械套用线性示例。
4. **验证并回报**：检查新的 base/head、实际 diff 与自身改动范围，补充受基线变化影响的行为检查，回报处理的目标 SHA、结果及阻塞。已推送分支若需非快进更新，只有相应授权下才以明确旧远端 SHA 的 lease 推送；本地同步不自动授权平台写入。主会话以真实新版本更新账本和验收证据，再决定后续集成。

rebase 有冲突时保留现场并报告，不自动选择 ours/theirs 或跳过提交；可确定的本任务冲突在授权范围内解决，再验证。未提交工作无法安全保存、缺少改写权限、目标不可取得或通知失败时记录具体同步阻塞；不宣称已更新，也不影响独立工作推进。缺少推送权限只阻塞相应远端更新，已授权的本地 rebase、验收和集成仍可继续。同步通知沿用直接人类消息授权，缺失或失败时由主会话通过 `wait_threads` 获取状态，待具备通知条件再协调。

## 汇总发布与验收

保留每项来源、增量 diff 和行为证据，再对集成 SHA 验证原始目标。发布时按可独立审查的逻辑变更分组，不机械按工作会话数量分 PR/MR，也不把整段提交历史重复加入每一层。检查实际 base/head，确认平台 diff 只含预期增量。

本地验收、组合验证、平台审查和实际合入分别记录。汇总或 rebase 形成新 SHA 时，保留来源映射并判断哪些验证需要更新；rebase 成功不代表行为正确。未授权正式合入时，交付已验证的本地集成或已发布 PR/MR 即可，按用户要求报告完成边界，不等待额外合并权限才承认交付。
