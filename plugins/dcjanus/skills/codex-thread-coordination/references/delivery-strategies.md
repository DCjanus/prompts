# 交付与集成方式

把工作会话的交付单位、依赖消费方式和最终发布形式分别确定。人类已明确要求 PR/MR 或项目要求每项独立审查时遵循该要求；其它情况下按依赖、审查成本和平台能力选用最轻的可追溯方式，不把一任务一 PR/MR 写成通用前提。

## 选择方式

| 方式 | 适用条件 | 工作会话交付 | 主会话责任 |
| --- | --- | --- | --- |
| 本地变更交付，汇总发布 | 共享仓库可访问，允许本地提交与集成，希望减少小 PR/MR 开销 | 独立 worktree 的 branch/ref、base/head SHA、变更范围和验证报告 | 逐项验收，在独立集成 worktree 中组合验证，再按授权汇总为一个或少量 PR/MR |
| 独立 PR/MR | 每项能独立合入，或人类/项目要求各自平台审查 | 分支、固定 SHA、URL 和验证报告 | 回读平台、验收并按合入权限处理 |
| 堆叠分支，可选堆叠 PR/MR | 消费者需要尚未正式合入的稳定前置，且允许维护分支依赖 | 直接父分支与固定父 SHA、增量 diff、head SHA；发布后补 URL | 管理父子关系、同步与组合验证，按平台规则发布和合入 |
| 仅工作区修改 | 未授权 commit 或仅要求本地修改 | worktree、明确 diff、验证报告及未提交状态 | 保留已有改动，验收本地结果，不扩大为提交或发布 |

无明确指定时，可采用本地变更交付、汇总发布，前提是相应 commit 和集成操作已有授权；权限不足时采用仅工作区修改。不要为选择交付形式重复询问已覆盖的权限。push、平台发布、正式合入和历史改写仍分别遵循授权。

本地集成只组合和验证已授权范围的变更，不更新受保护目标分支或远端。使用独立集成 worktree，记录起始基线及每项来源 SHA；指定一个集成人串行管理集成 ref。存在多仓库或跨 host 时，先确定可访问的 ref 或授权的传递方式，不假定工作会话共享磁盘。

消费者可以从约定的、已验收可消费的前置提交开始，不必等待一个并未要求创建的 PR/MR。简报记录直接父 SHA、已具备的契约、剩余缺口和验证条件；工作会话只能确认该版本可用，不能宣称它已正式合入。前置被修改时暂停受影响的消费，先由主会话确定新基线及同步责任，再重新验证相关路径。项目要求主线前置时，仍等待实际合入。

不是每个内部分支都必须单独满足最终发布门禁，但简报必须明确允许的临时缺口及可消费条件。最终组合必须满足项目门禁，不提前把已知损坏状态合入目标分支。不把整个任务图强行串成一个 stack：独立任务保持兄弟分支，只有真实依赖形成父子链；一个线性 stack 无法表达所有分叉依赖。

## 可选工具与能力核实

工具帮助维护 Git 关系和平台审查，不决定任务拆分、授权和验收。优先沿用项目现有工具，使用前读取本机版本、目标子命令帮助与项目配置；未安装工具时可继续用 Git 和平台 CLI，不自动安装或改全局配置。

- **Git Town**：跨 GitHub/GitLab 等平台的堆叠分支候选，可维护父子关系并创建 PR/MR。读取 [stacked changes](https://www.git-town.com/stacked-changes.html)、[GitLab connector](https://www.git-town.com/preferences/gitlab-connector.html)和 [同步策略](https://www.git-town.com/preferences/sync-feature-strategy.html)。默认 merge 同步与 rebase/compress 的历史影响不同；使用前核实实际配置、目标 remote 和命令涉及的分支，不让工作会话各自运行全栈同步来修改其它会话正在工作的 ref。
- **GitHub `gh stack`**：目标仓库原生 stack 可用且符合其线性历史、同仓库分支等规则时使用。普通父子分支 PR 与原生 stack 元数据是不同能力；不能仅凭组织/个人身份、旧记录或列表接口成功认定当前创建及合入能力。读取 [当前规则](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests)，合入上层可能包含下层，须核实整组权限与门禁。
- **GitLab `glab stack`**：先读取 [本机与官方帮助](https://docs.gitlab.com/cli/stack/)确认实验状态和 `save`、`sync`、`amend` 的真实副作用；不能将自动 stage、commit、push、创建 MR 或 rebase 看成一次普通的状态同步。原生 [stacked MR 展示](https://docs.gitlab.com/user/project/merge_requests/reviews/stacked_merge_requests/)与 CLI 能力分别核实，尤其是自建实例的版本。

并行 worktree 共享 Git 引用和部分工具元数据，工具宣称支持 worktree 不证明同时写 stack 安全。主会话协调唯一的 stack/ref 管理归属，工作会话只操作已分配分支；涉及同步或改写其它分支时先交接，不在执行中的工作树下移动其基线。

## 汇总发布与验收

保留每项来源、增量 diff 和行为证据，再对集成 SHA 验证原始目标。发布时按可独立审查的逻辑变更分组，不机械按工作会话数量分 PR/MR，也不把整段提交历史重复加入每一层。检查实际 base/head，确认平台 diff 只含预期增量。

本地验收、组合验证、平台审查和实际合入分别记录。汇总或重写形成新 SHA 时，保留来源映射并判断哪些验证需要更新；stack 工具的 restack 成功、创建链接或自动重定向不代表行为正确。未授权正式合入时，交付已验证的本地集成或已发布 PR/MR 即可，按用户要求报告完成边界，不等待额外合并权限才承认交付。
