# 并行开发策略

主会话负责提高有效并行度，工作会话负责一个明确的交付范围。以下策略服务于原始需求和项目门禁，不额外授权新会话、平台写入、合并或后台运行。

## 拆成独立交付，而不是文件碎片

读取相关源码、调用关系和项目检查入口后，按可观察行为或独立问题域拆分。每项任务应有明确产出、验收条件、改动归属和输入契约；仅因文件不同而拆分，或把一个小改动拆成实现、测试、文档三个互相等待的会话，通常增加交接成本。

用三个问题检查候选拆分：

1. 任务是否能依据已存在且稳定的输入独立实现和验证？缺少前置产出时记录真实依赖，不让工作会话猜另一个会话将提供的接口。
2. 任务是否修改相同的行为契约或共享结构？文件互不重叠也可能存在语义依赖；共享文件也不必然意味着逻辑依赖。少量可预测的独立编辑可以并行，但要指定重叠部分的集成人和合并后检查；高耦合编辑应合为一项或串行。
3. 独立交付是否值得一次启动、探索、验证和审查，以及选用平台发布时的 PR/MR 成本？把紧密相关的短依赖链或零碎机械改动交给同一工作会话。无法确定边界时先做一次有明确问题和输出的调查，再拆实现，避免多个会话重复研究全仓库。

若多项任务都需修改同一个共享契约或热点，先由一个任务稳定接口、扩展点及适用的兼容行为，再并行消费者。共享登记、统一配置或组合接线即使新增项不同，也指定一个工作会话负责汇总编辑；消费者交付接线需求，不各自顺带修改同一共享结构。基础任务必须明确可消费条件及验证缺口；正式合入主线的变更须满足项目门禁，不能为了形成并行窗口，把已知损坏的中间状态先合入主线。

派工前按 [交付与集成方式](delivery-strategies.md) 确认依赖的消费和最终发布形式。允许本地交付和集成时，已验收固定 SHA 的前置可以供消费者使用，无需先建 PR/MR 或合入主线。若项目要求主线前置，则按其策略安排；没有适用权限或策略时，把无法独立交付的前置与消费者合为完整任务，独立工作继续并行。已执行后才发现缺口时报告阻塞并调整未执行任务，不擅自合入目标或改平台 base。

## 按依赖就绪持续派工

用任务间的真实输入依赖形成有向无环图；出现环通常需要合并任务、先明确契约或重新切分。排他资源约束单独记录，不伪装成代码依赖。

为即将派工的任务核实真实路径、基线、契约和检查；后续任务先保留目标、区域和依赖。每次前置达到约定的可消费状态后，重新核实下一批范围，删去已被覆盖的工作并调整失效假设。不要提前给后续任务写死会被前置改动替换的路径和行号。

优先推进决定完成时间的依赖链，尤其是能解除多项阻塞的基础任务。预计工时仅用于排序，不作交付承诺。依赖已达到约定消费条件、资源已可用且存在执行容量时即可派工，无需等待其它独立任务全部完成。

例如已授权本地提交与集成时，A 稳定共享契约，B、C 消费它，D 是独立改进，E 验收 B、C 的组合行为：

- 初始可并行 A、D；B、C 的实现等待 A 的固定提交验收为可消费。
- A 达到消费条件后重新核实并派工 B、C，固定各自父 SHA，即使 D 仍未完成。
- A、B、C 本地集成后验收 E；D 不影响 E 时无需形成整批等待。最终按授权汇总发布，不把本地集成写成已正式合入。

等待前置的任务可以调查不依赖其结果的问题，但不得提前实现假想契约。主会话在有界等待间隙处理已交付结果、解除依赖和资源请求，不重复替工作会话完成已派出的实现。

## 用实际瓶颈决定并行度

不固定会话数量，也不默认开满所有可用位置。先启动有明确独立性且资源可承受的就绪任务，再根据实际进展扩展并行度；遵循人类给定的模型、额度和资源限制。

把构建与验证吞吐、排他资源占用、审查积压和集成速度一起考虑。若任务大部分时间等待同一资源，或启动更多会话只让验证和审查积压，减少新增派工、缩小争用范围或重新拆分。主会话先处理关键路径上的已交付任务，及时释放资源和解除依赖。

派工只提供原始目标中的相关要求、源码入口、已有决策、接口契约、禁止范围和交付要求；让工作会话读取必要原始证据，不重复搬运整段历史，也不只传主会话结论。模型选择仍遵循人类和项目要求，不为提速自行替换明确指定的模型。

可在既有账本记录启动、实现、验证、等待资源、审查和集成的粗略耗时。用端到端交付时间、返工和等待判断拆分是否有效；没有可比基线时只报告观察，不宣称并行带来某个倍数的提速，不新增遥测服务。

## 并行实现，逐项集成，验收组合

每项交付先检查范围、契约、真实 diff 和对应 head 的验证。主会话在本地集成权限内按依赖逐项组合，正式合入另遵循合并权限和项目门禁；无依赖的交付可按就绪情况安排，不为固定编号等待尚未完成的任务。实际 Git 引用写入与共享集成环境串行协调。

出现冲突时核对两项任务的目标和契约，由明确的归属会话处理；不得机械保留某一侧。即使 Git 无文本冲突，也要检查接口连接、共享状态和边界行为。重叠范围扩大或契约改变时，暂停受影响的派工并重新核实；无关任务继续。

在组合后的确定 SHA 上验证原始目标的关键路径及跨任务契约，按风险选择项目检查和集成验证。不能用“各工作会话测试通过”证明组合行为，也不为每个微小任务机械重复整套昂贵检查；项目要求的门禁仍完整执行。集成缺陷交给明确的工作会话修复并复验，主会话保留验收责任，不让多个会话同时追同一个缺陷。

需要协调暂不可独立合入的变化时，按约定本地组合或采用适用的堆叠审查，验证完整目标后再发布与合入。不默认改动既有 PR/MR base，也不采用先红后绿的目标分支合入方式。

- [Ordewell：计划中的并行与集成验证](https://github.com/ordewell/ordewell/blob/e221ecff8d25dbc7dc9cc545f424f10dea62f239/packages/core/src/services/PlanPrompts.ts)及 [交付落地状态](https://github.com/ordewell/ordewell/blob/e221ecff8d25dbc7dc9cc545f424f10dea62f239/packages/core/src/services/Landing.ts)：借鉴共享编辑单一归属、组合验收及实现与实际落地分离，不采用其自动合并、完成标记或模型默认值。
